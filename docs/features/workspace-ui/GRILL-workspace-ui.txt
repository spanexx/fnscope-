DECISION 1 — Real scopes live on the server, not in the browser
----------------------------------------------------------------
LOCKED ANSWER [agent decision]
  A project scope is one independently scanned manifest plus a server-side registry entry.
  The UI never slices one graph into fake projects. The demo scopes (`fnscope-crates`,
  full tree, `sample-nlp-app`) are configured scopes, not hardcoded client filters.

WHY
  The prototype's three scopes are slices of one self-scan. They keep one `rootDir`, retain
  cross-scope `calledBy`/`callsFnId` edges, and cannot resolve Node invokes per project. A
  client-only scope switch would look isolated while leaking fixture callers and the wrong
  source root. Real isolation requires per-scope graphs and per-scope invoke roots.

SOURCE
  `docs/features/workspace-ui/research/discovery-synthesis.md` ("Scope model");
  server/scope scout brief; prototype `wireframe/fnscope-workspace/generate-data.js:193-242`;
  `crates/fnscope-server/src/lib.rs:41-55,100-138,332-361`;
  `crates/fnscope-core/src/scan.rs:504-510`.

ALIGNMENT
  Serves the user's "zero cross-repo pollution" requirement and makes the project switcher
  truthful. It rules out client-side slicing as the shipped implementation.

DECISION 3 — Workspace config + CLI; single-scope behavior stays unchanged
--------------------------------------------------------------------------
LOCKED ANSWER [agent decision]
  A local `fnscope.workspace.json` plus `--workspace`, repeatable `--scope ID=PATH` and
  `--default-scope` configure scopes. Relative paths resolve against the config file. With no
  workspace configuration, `open` behaves exactly as today: one scan, one implicit `default`
  scope, `.fnscope/fn-graph.json`. Workspace mode writes
  `.fnscope/scopes/<id>/fn-graph.json`. Do not change locked `ScanOptions` defaults or
  auto-discover repositories.

WHY
  The product is local-first and environment-agnostic. Auto-discovery would silently expose
  unrelated trees; changing default excludes would alter locked scan behavior. An explicit
  config is reviewable, testable and portable.

SOURCE
  `docs/contract/rust-api.md:132-155,203-210`; server/scope scout brief ("Configuration and
  discovery"); `crates/fnscope-cli/src/{cli,main}.rs`; `crates/fnscope-core/src/scan.rs:25-69`.

ALIGNMENT
  Preserves the existing CLI contract and gives real projects a deliberate opt-in. The demo
  workspace config can name the prototype's three scopes without hardcoding them in the UI.

DECISION 4 — Default scope is configured/active, not a hardcoded demo name

DECISION 7 — Real manifest data only: full source and steps, no curated overrides
----------------------------------------------------------------------------------
LOCKED ANSWER [agent decision]
  The UI renders `FnRecord.sourceCode`, `FnRecord.steps`, `returns`, `errors`, `calledBy`,
  parameters and metadata from the served manifest. Remove the prototype's curated story
  overrides, 3,200-character source truncation and 14-step embedding. Keep the six-step initial

  Curated narratives inventory behavior the manifest does not contain and break trace joining.

  the underlying data must be real.

DECISION 8 — Invoke is real per scope; mode is a server capability
------------------------------------------------------------------
LOCKED ANSWER [agent decision]

DECISION 10 — One reset boundary for scope/function changes
------------------------------------------------------------
LOCKED ANSWER [agent decision]
  Switching scope or function resets selection-derived state: trail, drawer run/args/error,
  step expansion, and any in-flight invoke. A scope switch remounts the explorer by scope id.
  An in-flight run is cancelled or ignored via a request token/AbortController; a late response
  must never attach to a newly selected function.

WHY
  The prototype resets some state but not all (mode, view, drawer tab, banner) and its delayed
  run can land on the wrong selection. Stale state is a correctness bug, not cosmetic.

SOURCE
  Prototype `wireframe/fnscope-workspace/app.js:79-102,968-1053,1055-1101`; wireframe scout
  brief (gaps 5, 7); UI architecture brief (state reset).

ALIGNMENT
  Makes navigation deterministic and prevents cross-scope/selection leakage.

DECISION 13 — Security hardening now; vulnerability scanning later
------------------------------------------------------------------
LOCKED ANSWER [agent decision]
  Harden the local server: loopback default, Host/Origin checks, no CORS, scope-id whitelist,
  canonicalized scope roots and Node module paths, manifest size/count limits, Node process
  timeout/tree cleanup and a concurrency cap, no source in logs. Do not implement vulnerability
  detection in this pack. Leave stable identity (`scopeId + fnId + stepId + astHash`) and a
  separate future findings model/plugin boundary documented as future work.

WHY
  Multiple manifests plus Node execution increase the attack surface. The user asked for a
  future security direction, not a half-built scanner. Mixing the two would bloat this pack and
  weaken both.

SOURCE
  Product scout brief (security extension points, privacy, acceptance checks); server/scope
  scout brief (security/privacy); `crates/fnscope-server/src/lib.rs:332-431`.

ALIGNMENT
  Protects the current product and preserves a clean extension seam for security analysis.

DECISION 16 — Human gates remain; local feature-branch commits are allowed
---------------------------------------------------------------------------
LOCKED ANSWER [agent decision]
  The orchestrator may commit logical changes on `feature/workspace-ui` for review, but does
  not merge to `main`, open a release, or move `stable` without the user's explicit approval.
  The PR/review gate is mandatory. Under the documented fast-mode exception, a subagent may
  commit locally inside its own worktree; it never merges, pushes, or touches the integration
  branch. The orchestrator reviews and cherry-picks, then commits the integrated tree.

WHY
  Delegation covers design and implementation decisions, not the human merge/release gate.
  Isolated local commits make review and cherry-picking possible without polluting `main`.
  Workers editing without commits would force the orchestrator to extract patches from many
  dirty worktrees, which is slower and loses files on renames.

SOURCE
  Goal skill `decisions.md:50-58,83-100`; `AGENTS.md` commit/worktree rules;
  `.orchestrator/profile.md` fast-mode exception; orchestrator skill "Worktrees, commits and
  gates".

ALIGNMENT
  Keeps the loop moving while preserving the user's control over the public branch. The
  exception is recorded in every worker brief; `AGENTS.md` remains the general rule.
