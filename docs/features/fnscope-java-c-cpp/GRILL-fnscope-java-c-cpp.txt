DECISION 1 — Java, C and C++ ship as one batch
----------------------------------------------
LOCKED ANSWER [agent decision]
  Implement the three adapters in three isolated worktrees (J30 Java, J31 C,
  J32 C++), review them together (J33), register them together (J34), gate all
  three together and land them as one logical change, commit `5408cad`.

WHY
  All three need the same unowned edits: three grammar dependencies, three
  `pub mod` lines, three `register(...)` calls, two id-table rows per language
  and five default scan globs. One batch amortizes that shared registration
  and produces one gate verdict and one commit instead of three partially
  wired adapters. Keeping the implementation worktrees disjoint preserves the
  repo's bounded write windows.

DECISION 2 — The C module is named `c_lang`
-------------------------------------------
LOCKED ANSWER [agent decision]
  The directory and module are `crates/fnscope-parser/src/c_lang/`. The public
  type stays `CAdapter`, the id stays `"c"` and the suffix stays `"c"`.

WHY
  `c` alone is easy to confuse with the `fnscope-parser` crate and with the C

DECISION 3 — C does not claim `.h`
----------------------------------
LOCKED ANSWER [agent decision]
  `CAdapter::extensions()` is exactly `&["c"]`. Header files are excluded, as
  are prototypes inside `.c` files; only top-level `function_definition`
  nodes become callables.

WHY
  A header repeats a declaration that has an implementation in a `.c` file.
  Indexing both would create duplicate functions with different ids and
  pollute the bidirectional call graph. The same reason applies to prototypes.

SOURCE
  `docs/contract/adapters/c.md:23-27` — "Header files are not claimed. `.h`
  files repeat declarations that already have an implementation in a `.c`
  file; discovering both would add duplicate functions with different ids and
  pollute the call graph."
  `crates/fnscope-parser/src/c_lang/mod.rs:8-10` — the same module note;
  `:38-40` — extensions excludes headers.
  Review `.reports/reviews/J30-J32.md:37` — "`.h` deliberately excluded";
  `:40` records top-level `function_definition` only, with prototypes and
  nested definitions excluded.
  `tests/fixtures/c_app/README.md:25-26` — "Header declarations are
  deliberately not discovered: the adapter claims only `.c`."

ALIGNMENT
  Avoids duplicate ids and dangling edges, serving iteration 16's evidence
  (3) "a mixed polyglot fixture scans correctly in one manifest" and the
  iteration 35 scan that reported 0 dangling edges.

DECISION 5 — Java callables are qualified by their class
---------------------------------------------------------
LOCKED ANSWER [agent decision]
  Only `class_declaration`, `interface_declaration` and `record_declaration`
  at the file root are walked. Every callable is `ClassName.method` with
  `class_name = Some("ClassName")` and `FnKind::Method`; a constructor is
  `ClassName.ClassName`. Record components feed the type index. Nested local
  classes are not descended.

WHY
  Java has no module-level functions: a method without its type would have an
  ambiguous name and could collide with a method of another class. Qualifying
  by class, and sorting/deduping by `(line, qualified_name)`, keeps ids stable
  and the call graph unambiguous.

SOURCE
  `docs/contract/adapters/java.md:35-37` — "Only these three kinds are walked
  at the root. Java has no module-level functions, so a method is never
  recorded without a type."
  `:68-70` — "Every callable is `ClassName.method` with
  `class_name = Some("ClassName")` and `FnKind::Method`".
  `crates/fnscope-parser/src/java/discover.rs:46` (root kinds), `:101`
  (`format!("{class_name}.{name}")`), `:124` (`class_name`), `:75-76` (sort
  and dedup).
  Review `.reports/reviews/J30-J32.md:26` — "qualified name `ClassName.method`

DECISION 6 — Grammar wrapper nodes are unwrapped in the adapter, not in core
---------------------------------------------------------------------------
LOCKED ANSWER [agent decision]
  Each adapter names and unwraps the wrapper nodes of its own grammar and
  keeps a fallback to the original node when a wrapper is absent. Java walks
  `class_body`, `interface_body`, `formal_parameters`, `block` and switch
  groups; C unwraps `field_declaration_list` for records and handles
  pointer/parenthesized declarators; C++ unwraps `field_declaration_list`,
  `condition_clause`, `argument_list` and `init_declarator` and checks for a
  `statement_list` defensively. No core file changes.

WHY
  These grammars insert nodes between a block or declaration and the fact the
  adapter expects as a direct child. The Python/Go batch had already failed
  nine tests for exactly this reason (ledger iterations 28-29). Unwrapping in
  the adapter keeps grammar knowledge behind the plugin seam.

SOURCE

  wrapper nodes explicitly".
  Ledger iteration 30 (`.reports/goal-build-fnscope.md:295`) — dispatch with

DECISION 7 — Error `when` keeps the enclosing condition verbatim, parentheses included
--------------------------------------------------------------------------------------
LOCKED ANSWER [agent decision]
  `ErrorSpec.when` is the exact text of the nearest enclosing `if (...)`
  condition, including its parentheses. For `if (text.isEmpty()) { throw ...
  }` the value is `(text.isEmpty())`. A throw with no guard uses the
  deterministic fallback `explicit throw`. The Java test assertion, not the
  production code, was corrected in iteration 34.

WHY
  The locked spec says to extract the enclosing `if (...)` condition *as*
  `when`; stripping the parentheses would change that text. The sibling Rust,
  Python and TypeScript adapters report the same text. Iteration 34 recorded
  a mismatch between a test expecting no parentheses and the code following
  the spec; per L2 the contract decides which side is wrong.

DECISION 9 — One registration job owns the shared files
--------------------------------------------------------
LOCKED ANSWER [agent decision]
  J30/J31/J32 own only their adapter module, contract doc and fixture. J34
  alone edits the shared files: root and parser `Cargo.toml`, `Cargo.lock`,
  `crates/fnscope-parser/src/lib.rs`, `crates/fnscope-parser/src/adapter.rs`
  and the default globs in `crates/fnscope-core/src/scan.rs`. Registration is
  never done inside an adapter worktree.

WHY
  Concurrent writes to `adapter.rs` or a manifest would overwrite one
  another. Deferring registration also keeps each adapter reviewable on its
  own and lets one gate verify the combined wiring and the lockfile update.

SOURCE
  Ledger iteration 31 (`.reports/goal-build-fnscope.md:307`) — "Pivot: single
  registration job after review, as before."
  Iteration 32 (`:314`) — "one registration job owns the shared registry
  files so parallel jobs never collide."
  Review `.reports/reviews/J30-J32.md:65-90` — "These are unowned files. No
  agent edited them" (`:67`), the Cargo.lock note at `:69`, and numbered
  registration notes for Java `:71-76`, C `:78-83`, C++ `:85-90`.
  `docs/contract/adapters/java.md:8-10`, `c.md:8-10`, `cpp.md:5-6` — each

  `git show --stat 5408cad` — the shared files and all adapters land in the

ALIGNMENT
