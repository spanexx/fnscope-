DECISION 1 — A registry trait, not a growing Lang enum with per-language branches
--------------------------------------------------------------------------------
LOCKED ANSWER [agent decision]
  Put all language knowledge behind `LanguageAdapter: Send + Sync` (six methods:
  `id`, `extensions`, `discover`, `analyze`, `collect_types`,
  `resolve_return_fields`) and `Registry` in
  `crates/fnscope-parser/src/adapter.rs`. Keep `Lang` public only in `types.rs`
  for compatibility with the original entry points; core neither imports nor
  matches on it. Register one `TypeScriptAdapter` per suffix (`.ts`, `.tsx`,
  `.js`, `.jsx`) so the original grammar choice is preserved byte-for-byte.

WHY
  Iteration 15 answered "Rust scan returned 0" by adding `Lang::Rust` and a
  `.rs` branch in core. Iteration 16 expanded that to many languages; scaling
  the enum-and-match pattern would make core the owner of every grammar, spread
  `match` arms across crates and break disjoint file ownership. The concept
  calls this the anti-pattern and states the rule: a new backend is a plugin,
  not a branch in the graph builder. Four TS-family instances are needed
  because `discover`/`analyze`/`collect_types` receive no path, so one instance
  could not select the TSX grammar for `.tsx` and JavaScript for `.jsx`.

SOURCE
  Ledger iteration 15 (`.reports/goal-build-fnscope.md:170-176`) — the `Lang::Rust`
  approach; iteration 16 (`:178-188`) — the expansion quoted above and the
  outcome "adding a language requires ZERO changes to core graph builder,
  schema, enricher or UI" (`:181`).
  `docs/concepts/language-adapter.md` — "Anti-pattern: per-language `if`
  branches in core" and "The invariant".
  `docs/contract/adapter-api.md:12-32` (trait/registry sketch), `:62-83`
  (four documented deviations with reasons), `:100-123` (core change).
  Shipped code `crates/fnscope-parser/src/adapter.rs:17-48` (trait),
  `:54-91` (Registry), `:94-96` (`registry()`), `:62-77` (four TS-family
  registrations).

ALIGNMENT
  Serves L9 ("A new backend is a plugin, not a branch in the graph builder",
  `docs/ethics/lessons.md:187-200`) and iteration 16's zero-core-change
  outcome. The sealed grammar boundary is what makes every later language
  batch (Python, Go, and the rest) an adapter-only change.


DECISION 2 — Core stays language-neutral: one extension lookup per file
------------------------------------------------------------------------
LOCKED ANSWER [agent decision]
  `fnscope-core/src/scan.rs` imports only `LanguageAdapter` and `Registry`.
  Production code performs exactly one `registry.for_extension(extension)`
  call per discovered file, then calls `adapter.collect_types`,
  `adapter.discover`, `adapter.resolve_return_fields` and `adapter.analyze`.
  There is no `Lang` import, no per-language `if`/`match`, and no change to
  ids, hashes, name-to-id maps, `calledBy` edges or manifest assembly.

WHY
  File walking, id and hash assignment, edge resolution and manifest I/O are
  identical for every grammar. Keeping that code language-free means a defect
  or addition in one adapter cannot regress another language through core.

SOURCE
  `docs/contract/adapter-api.md:100-123` — the one dispatch point and the
  untouched core operations.
  Shipped `crates/fnscope-core/src/scan.rs:8` (imports), `:217-225` (`scan`),
  `:227-236` (`scan_with_registry`), `:253-281` (file loop, sole lookup at
  `:262-268`), `:285-314` (id/name/edge passes).
  Review `.reports/reviews/J21.md` checklist 4 and its re-review checklist 4:
  "standalone `Lang` count in `scan.rs` = 0".

ALIGNMENT
  Directly enforces iteration 16's "ZERO changes to core graph builder" and
  L9's checkable procedure ("diff the change and confirm only the adapter
  registry plus the new adapter ... moved").


DECISION 3 — Adding a language must not touch core, schema, enricher or UI
--------------------------------------------------------------------------
LOCKED ANSWER [agent decision]
  A new language is delivered as: an adapter implementing the six trait
  methods, its registry entry, its fixture and its unit + integration tests.
  Any diff that also touches `fnscope-core`'s graph builder, `fnscope-model`,
  `fnscope-enrich`, `ui/`, `docs/contract/rust-api.md` or the schema version is
  a stop-and-review condition recorded in `docs/drift.md`, not a branch to add.

WHY
  The schema, enricher and UI consume `FnGraph` and have no grammar knowledge.
  Letting a language leak into them would produce per-language fields, runtime
  labels and UI cases, defeating the single manifest that iteration 16
  acceptance evidence (3) requires ("a mixed polyglot fixture scans correctly
  in one manifest").

SOURCE
  Ledger iteration 16 (`.reports/goal-build-fnscope.md:181`, `:182`) — the
  outcome and acceptance evidence (3) and (5).
  `docs/concepts/language-adapter.md` — "What core owns", "The invariant",
  "How to add a language (recipe)".
  `docs/contract/adapter-api.md:100-123` — "No edit to ... is part of this
  recipe. If any step appears to require one, stop and raise it as
  architecture drift".
  `docs/ethics/lessons.md:187-200` (L9) and `docs/ethics/boundary-discipline.md:50`.
  Later confirmation: ledger iteration 24 (`:251`) routes registration to a
  separate job so language work never edits core directly.

ALIGNMENT
  The seam keeps `tool: "fnscope"`, `schemaVersion: "1.0.0"` and the locked
  `DiscoveredFn`/`BodyAnalysis`/`Step`/`ErrorSpec`/`ReturnShape` types stable;
  J22 confirmed no model file changed (`.reports/reviews/J21.md` checklist 2).


DECISION 4 — `scan_with_registry` is the single injection seam
---------------------------------------------------------------
LOCKED ANSWER [agent decision]
  Add one public function `scan_with_registry(options, out_dir, generated_at,
  &registry)`. `scan` keeps its original signature and becomes a thin delegate
  that builds `registry()` and calls `scan_with_registry`. No global mutable
  registry is introduced; a caller or unit test injects the registry it wants.
  `ScanOptions`, `ScanReport`, `write_manifest` and `read_manifest` are unchanged.

WHY
  The proof that adding a language needs no core edit is that a foreign
  adapter can be passed into core from outside. A global registry would hide
  that dependency and make tests order-dependent; a new function with an
  explicit parameter keeps the seam visible and the default path unchanged.

SOURCE
  `docs/contract/adapter-api.md:52-60` ("Core injection seam ... a new public
  function was needed so a caller ... can inject a registry without global
  mutable state") and `:100-123`.
  Shipped `crates/fnscope-core/src/scan.rs:217-225` (`scan` delegate) and
  `:227-236` (`scan_with_registry`).
  Test `crates/fnscope-core/src/scan.rs:623-711` (`FakeAdapter` claiming
  `.zig`, built-in scan empty, injected scan yields one function `zeta`).
  Review `.reports/reviews/J21.md` checklist 4 and 7.

ALIGNMENT
  Establishes the acceptance evidence that an unregistered suffix yields
  nothing while an injected adapter is selected — the registry seam is
  observable without editing core.


DECISION 5 — One registration job per batch; worktrees stay disjoint
---------------------------------------------------------------------
LOCKED ANSWER [agent decision]
  Adapter implementation jobs own only their adapter module, contract doc and
  fixtures. They record the exact registration edits they need but do not make
  them. One later orchestrator-delegated job applies the shared edits
  (manifests, `lib.rs`, `adapter.rs`, core default globs). Two worktrees never
  write the registry or a manifest at the same time.

WHY
  Concurrent worktrees editing `adapter.rs` or `Cargo.toml` would overwrite
  each other and make a review diff unattributable. Splitting registration
  into one reviewed job also lets a single gate verify the combined wiring.

SOURCE
  Ledger iteration 20 (`.reports/goal-build-fnscope.md:215-220`) — every
  subsequent brief states that an independent reviewer audits it, pastes the
  checklist, and forbids cargo, temp files and commits.
  Ledger iteration 24 (`:251`) — "per-language adapters are registered by a
  separate orchestrator-delegated job after review, so two worktrees never
  edit the registry file".
  Iteration 25 (`:259`) repeats the pivot for Python/Go; iteration 26 (`:263`)
  dispatches J26 for the registration edits.
  Review `.reports/reviews/J21.md` checklist 9 — scope limited to owned paths.

ALIGNMENT
  AGENTS.md "Parallel work rule" and "one logical change = one commit". The
  registry remains a single, reviewable seam instead of a merge conflict.


DECISION 6 — Paired reviewers: implementation and review are separate jobs

  implementation authority. The review notice and checklist are carried in
  the brief verbatim; no job self-approves. A reviewer PASS means "no defect

DECISION 7 — A false rustfmt PASS becomes L11, not a discarded incident
------------------------------------------------------------------------
LOCKED ANSWER [agent decision]
  Treat `rustfmt --check` as formatting evidence only. After J21's clean
  format marker and J22's PASS were followed by 12 `E0425` errors, record the
  rule as L11: a syntax/format check is NOT a correctness check. Reviewer
  briefs gain a semantic-sanity item (truncated/undefined identifiers, wrong
  arity); byte normalization uses `tr -d '\r'` and is verified with
  `tr -cd '\r' < file | wc -c` == 0 — never `sed 's/\r$//'`.

WHY
  The merge had stripped the final `r` from `adapter`, `declarator`, `inner`
  and `member` (`adapte`, `declarato`, `inne`, `membe`) because a normalization
  command treated `\r$` as a literal trailing `r`. Formatting was green while
  the code could not compile. The reviewer had accepted the format marker as
  correctness even though its own "Known limits" admitted it had not re-run
  formatting.

SOURCE
