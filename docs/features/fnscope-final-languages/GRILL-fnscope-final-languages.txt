DECISION 2 — Kotlin grammar: `tree-sitter-kotlin-ng` replaces `tree-sitter-kotlin`
--------------------------------------------------------------------------------
LOCKED ANSWER [agent decision]
  The Kotlin adapter uses `tree-sitter-kotlin-ng = "1.1"` in both manifests
  and `tree_sitter_kotlin_ng::LANGUAGE.into()` in `src/kotlin/mod.rs:45`.
  `tree-sitter-kotlin 0.3.8` is deliberately absent. Grammar node kinds were
  remapped for the -ng grammar and all 14 Kotlin tests were preserved.
  This gap is D-6 in `docs/drift.md`.

WHY
  The old grammar pins `tree-sitter >= 0.21, < 0.23`, and tree-sitter declares
  `links = "tree-sitter"`, so Cargo allows only one such package; 0.21 and the
  workspace's 0.25 cannot coexist in one binary. The -ng crate depends on
  `tree-sitter-language 0.1`, exports `LANGUAGE`, and lists tree-sitter 0.24
  as dev-only, so it does not link a second native runtime.

SOURCE
  Drift D-6 (`docs/drift.md:57-61`) — opened against the "native `links`
  conflict", closed with the -ng replacement and a green gate.
  Ledger iteration 37 (`.reports/goal-build-fnscope.md:347-354`) records:
  Diagnosed a native `links = "tree-sitter"` conflict from
  tree-sitter-kotlin 0.3.8 (pins 0.21/0.22) coexisting with workspace
  tree-sitter 0.25. Found `tree-sitter-kotlin-ng 1.1.0` (uses
  tree-sitter-language 0.1, exports `LANGUAGE`) as the compatible replacement.
  Contract `docs/contract/adapters/kotlin.md:30-52` — verified crate source
  facts and the removal of all unsafe code.
  Review `.reports/reviews/J35-J39.md:162` — the registration note that the
  old grammar "pins tree-sitter >=0.21,<0.23" and would link a second runtime.
  Shipped code `crates/fnscope-parser/src/kotlin/mod.rs:43-45`; manifests
  `Cargo.toml:37` and `crates/fnscope-parser/Cargo.toml`.

ALIGNMENT
  Iteration 16's zero-core-change plugin invariant: a grammar swap stays
  inside one adapter plus the dependency lines. D-6 is Resolved, not deleted
  (L6, `docs/ethics/lessons.md:137-147`); the gate in iteration 42 is green.


DECISION 3 — The raw-pointer bridge was judged sound but rejected
-----------------------------------------------------------------
LOCKED ANSWER [agent decision]
  The `mem::transmute` bridge in the original Kotlin adapter is deleted. The
  soundness analysis stays in the record as analysis only; it is not a reason
  to merge the old grammar. No `unsafe` bridge code remains in `src/kotlin/`.

WHY
  Soundness and buildability are different questions. The review proved the
  transmute was bit-preserving (`repr(transparent)` thin pointers, ABI 14 in
  the workspace range 13..=15, no double-drop), but that says nothing about
  Cargo's native `links` uniqueness rule. Removing the unsafe code is simpler
  than maintaining a bridge around a dependency that cannot be linked.

SOURCE
  Review `.reports/reviews/J35-J39.md:48-69` — heading "Judgement on the
  Kotlin bridge (`kotlin/mod.rs:44-47`) — SOUND, not UB", with the repr, ABI
  and ownership reasoning; `:151` — "No Kotlin-bridge finding: the transmute
  is sound (see judgement above)."
  Ledger iteration 36 (`.reports/goal-build-fnscope.md:340-346`) — "Kotlin's
  raw-pointer bridge was explicitly judged SOUND (repr(transparent) thin
  pointers, ABI 14 supported, no double-drop)."
  Drift D-6 closure (`docs/drift.md:61`) — "The pointer-bridge analysis

DECISION 7 — Node invocation remains TypeScript/JavaScript-only
---------------------------------------------------------------
LOCKED ANSWER [agent decision]
  The five new adapters add parsing only. There is no executor for Kotlin,
  C#, Ruby, PHP or Swift; invoking one of their functions returns the
  deterministic simulated trace (usually with an `error` field describing
  the fallback). `universal` / `node20` stay as recorded runtime labels,
  not claims that Node can run these languages.

WHY
  The locked invoke semantics are a Node runner for TS/JS exports with a
  simulate fallback. Giving the new languages an executor would change the
  server contract and violate the zero-core-change plugin invariant; the
  labels must stay stable so schema and enricher need no language branch.

SOURCE
  `docs/features/fnscope-base/PRD-TRD.md:250-257` — "Node invocation ...
  remains a TypeScript/JavaScript runner and is not an executor for ... C#,
  Kotlin, Ruby, PHP or Swift"; non-TS/JS invoke "yields the deterministic
  simulated trace".
  `docs/STATUS.md:267-271` — "**Only TypeScript/JavaScript are executed.**"
  `docs/contract/adapters/php.md:146-150` and
  `docs/contract/adapters/swift.md:164-168` — runtime labels are execution
  labels, not real execution.

ALIGNMENT
  Base PRD-TRD section 9 invoke semantics; iteration 16's invariant that no
  enricher, server or UI change is needed for a new language.
